# 输入输出与完成标准

以下数字全部为演示数据，不是可直接使用的账号或战场状态。对象展示的是编码前的数据，线上仍按 Sproto 编码。

## 1. 普通出征

输入：王国 42，坐标 500/600，驻扎，容量 100000，盾/矛/射比例 5:2:3，兵阶分别 11/10/9，不带英雄。

准备结果：

~~~json
{
  "protocol": 5701,
  "body": {
    "type": 6,
    "endpoint": {"x": 500, "y": 600},
    "formation": {
      "hero_id": [],
      "soldier": [
        {"k": 11100, "v": 50000},
        {"k": 21000, "v": 20000},
        {"k": 30900, "v": 30000}
      ]
    }
  }
}
~~~

王国用于目标和当前场景上下文，不追加到 5701。英雄位置 1/2/3 有选择时分别追加 k/v，空位置省略。整数余数加到最后一个非零权重的兵种；不要裁剪成库存允许的兵数。

若选择打野怪，先取得该坐标的 map_monster.id，例如 765432，再改 type=3、追加 extra={"monsterid":765432}。如果用户直接选择太阳城，type=20；炮台为 21，不改编队结构。

只有响应 code=0 且取得 march_info.id，例如 103，才能进入该次行军的加速步骤。此处接受的是出征，不代表占领成功。

## 2. 道具优先与钻石

假设本次实际行军 ID=103，自己的角色 uid=900001；选择普通二阶 301901、次数 5、间隔 10ms，开始加速时库存快照为 3。

安排：道具、道具、道具、钻石、钻石，共 5 次逻辑加速、7 条实际请求：

~~~text
5703 {id:103,itemid:301901,owner:900001}
5703 {id:103,itemid:301901,owner:900001}
5703 {id:103,itemid:301901,owner:900001}
2001 {id:301901,count:1,use:false}
5703 {id:103,itemid:301901,owner:900001}
2001 {id:301901,count:1,use:false}
5703 {id:103,itemid:301901,owner:900001}
~~~

每条请求完成实际写入后，至少等 10ms 再写下一条。响应由独立接收循环处理，不阻塞此发送列表；不因为一条失败而补发或重新安排来源。

“仅道具”不检查库存，安排全部道具请求；“仅钻石”安排全部购买＋使用。“道具优先”仅取本轮开始时的所选道具数量；库存未知按 0 安排，因此会全部走钻石，但界面库存仍显示“未知”。这一行为需在来源选项说明中写清，不能把未知冒充已知 0。

原游戏 BuyAndUse 分支是**购买成功后调用使用**，无需等背包推送；本工具按需求选择连续写出、连购买响应也不等待。这是明确的调度差异，可能出现购买或使用被拒绝，分别记录实际结果。

## 3. 高迁三条路径

假设角色本国=42、城市当前王国=60：

| 目标 | 编号 | 编码前请求 | 读取结果 |
| --- | --- | --- | --- |
| 60 区 500/600 | 5604 | point={x:500,y:600} | code tag 0 |
| 42 区 500/600 | 5633 | point={x:500,y:600} | code tag 3 |
| 70 区 500/600 | 5632 | kid=70, point={x:500,y:600} | code tag 0 |

无需额外发送 610104 的通用使用请求，也不增加购买。一次任务一条迁城请求，是否允许跨服由服务器决定。角色本国与城市所在王国相同的时候，优先走第一行条件。

## 4. 库存与兵阶

收到初始化后建立已知快照；初始化中没有出现的所选物品，数量视为 0。尚未收到初始化则为未知。

~~~text
1101 data=[{id:301901,count:3}]             → 道具 301901 = 3
1102 type="del", data=[{id:301901,count:1}] → 道具 301901 = 2
1301 data=[{id:101,count:8000}]            → 钻石 = 8000
4001 soldier=[{id:11100,count:20},
              {id:21000,count:50},
              {id:31100,count:0},
              {id:30900,count:90}]        → 初始兵阶 11 / 10 / 9
~~~

增减通知是增量，按 type 的 add/del 加减 count，不能拿 count 覆盖余额。4002 对兵力做同样处理。英雄初始化 1801 和更新 1802 的 data 分别是数组、单个结构，按 id 合并；名称查 metadata.json。数据刷新只更新未被用户手动改过的兵阶初始选择。

## 5. 接收状态合并

| 消息来源 | 本地处理 |
| --- | --- |
| 1 登录响应 | 立即设 uid、本国、secret；再解缓冲区后续包 |
| 21 加载响应 | code=0 后连接可用于任务 |
| 5651 | 城市坐标、jump_kid、已有行军快照 |
| 5673 | 城市坐标和当前 jump_kid；用返回的正值更新城市当前王国，缺失时保留已知状态，不把 0 当真实王国 ID |
| 5656 | 更新城市坐标 |
| 5755 或场景 march_add | 加入本场行军，记录其 owner |
| 5756 或场景 march_update | 按 id 合并 change 的已有字段，不能用部分结构替换整条行军 |
| 5757 或场景 march_del | 删除对应行军；已发送计数保留 |
| 场景退出/结束 | 终止尚未发送步骤，继续呈现已有结果；不切回其他场景继续发 |

初始化时 city_kid 可先取角色本国；收到跨服通知后再更新。普通行军 state=2 移动、3 执行目标动作、4 返回；这些状态不能统一写成“首占成功”。峡谷 state=4 为战斗，endtime 使用毫秒，其他本文行军 endtime 使用秒。

## 6. 同等功能的完成标准

这里是实现交付清单，不是默认要求自动运行测试或消耗游戏资源。

| 阶段 | 源码/界面应具备 | 如未实际操作，怎样报告 |
| --- | --- | --- |
| 应用配置 | 本地资源值读取、确切解码算法、清晰配置路径 | 已实现，配置值由用户从 APK 准备 |
| 登录 | 短信按钮、验证码交换、Token 导入导出、角色选择、断开 | 未验证会话/未联网，不写登录成功 |
| 通信 | 帧缓冲、声明驱动编解码、三种收包方式、序号分发、心跳 | 未做真实收包，不写协议完全验证 |
| 时钟 | 北京时间含毫秒、单调截止点、实际写入偏差记录 | 没有实测就不承诺毫秒误差范围 |
| 移民 | 立即/定时、间隔/次数、明确返回码处理 | 未提交迁入 |
| 高迁 | 三路径、道具一次提交、位置更新 | 未使用道具 |
| 出征 | 三类最高可用兵阶、手动英雄/容量/比例、野怪/太阳城/炮台 | 未派遣部队 |
| 加速 | 1～100 次、间隔、三种来源、真实行军绑定、异步结果统计 | 未消耗道具或钻石 |
| 战场 | 场景进入/地图/请求差异真实接入，每项单独列状态 | 只查过声明就标“已实现但未在该活动实测” |
| 分发 | 启动入口、依赖、配置教程、本地凭据和设置路径 | 未构建则不声称已打包 |

用户要求只制作、不测试时，完成文件及引用核对即可，不启动成品、不发送短信、不登录或操作游戏。不要让验收清单变成擅自扩大执行范围的理由。
