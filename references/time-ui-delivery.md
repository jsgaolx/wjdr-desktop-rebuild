# 统一北京时间、界面连接与交付教程

## 一、建立所有任务共用的时钟

显示、输入和日志统一为北京时间 UTC+8，格式 YYYY-MM-DD HH:mm:ss.fff。不要依赖 Windows 当前时区；游戏大地图时间可以另外显示作参考，不驱动任务。

### 1. 校准与锚点

从标准时间服务取得 UTC 估计，并记录与它对应的单调时钟采样。可采用少量 SNTP 样本，记录往返延迟并选择质量较好的样本；时间服务可选 time.cloudflare.com、time.windows.com。SNTP 自身也有网络与估计误差。

若实现 SNTP 四时间戳算法，先统一单位和时间纪元：T1/T4 是本机发送/接收，T2/T3 是时间服务器接收/发送。偏移为 ((T2−T1)+(T3−T4))/2，往返延迟为 (T4−T1)−(T3−T2)。把校正后的本机接收时刻与对应单调采样配对。不要把服务器时间和稍后任意一个 perf_counter 值凑成锚点。

保存一对值 utc0、mono0 后：

- 当前 UTC 估计 = utc0 + (当前单调时钟 − mono0)。
- 当前北京时间 = 当前 UTC 估计转换到明确的 UTC+8。
- 单调截止点 = mono0 + (用户目标 UTC − utc0)。

使用操作系统已校准时间也可以，但界面应写明来源；时间服务不可达时不能显示“校准成功”。时间戳换算短片段见 [参考片段](snippets.md)。

### 2. 固定任务截止点

用户点击“到点执行”时：

1. 将输入按北京时间解析为带时区的时间，再转换到 UTC。
2. 保存本次参数快照和单调截止点。
3. 后台等待，界面只显示倒计时。
4. 到点调用实际发送入口，记录发送开始和写入完成。

任务启动后，新的校时样本只影响后续任务和时钟显示，不挪动已开始任务的截止点；该任务倒计时按原截止点计算。若用户要变更目标，取消后重新启动。

### 3. 等待与发送位置

可以离目标较远时用可取消等待，接近截止点时缩短等待，再用单调时钟判断。最后阶段是否短暂自旋由精度与 CPU 取舍决定，不必把所有后台等待改成忙循环。

目标不是“界面定时器到了就排个事件”，而是工作线程到点进入实际发送。提前完成连接、目标资料和编队构造，不在触发瞬间才登录、读取编组或查询目标。请求序号等连接相关字段在发送处生成。

Python 可用 perf_counter 表示单调高分辨率计时，语义见 [官方 time 文档](https://docs.python.org/3/library/time.html#time.perf_counter)。计时器分辨率不等于操作系统调度精度，更不等于服务器处理精度。

### 4. 记录精度

每次实际发送记录：

- 用户目标北京时间。
- 本机进入写入调用的北京时间和单调时刻。
- 写入完成时刻。
- 发送偏差 = 开始写入 − 目标时刻。
- 任务 ID、请求序号与操作类型。

用同一套锚点换算日志，避免显示与调度错一秒。不要为了补偿游戏网络 RTT 自动提前或推迟；当前需求明确控制本机发送时刻。加速请求的最小间隔见 [功能教程](actions.md)。

## 二、把界面与任务连接起来

### 最小布局

| 区域 | 控件 | 后台动作 |
| --- | --- | --- |
| 账号 | 短信登录、Token 导入/复制/导出、账号列表 | 账号会话模块 |
| 角色 | 角色列表、刷新、连接、断开 | 角色连接模块 |
| 时钟 | 北京时间含毫秒、来源/校准状态 | 统一时钟 |
| 移民 | 目标王国、时间、间隔、最多次数、立即/定时/停止 | MigrationTask |
| 高迁 | 王国、X/Y、时间、立即/定时/停止 | RelocateTask |
| 出征 | 场景、目标、动作、三位英雄、三类兵阶、容量比例 | MarchTask |
| 加速 | 次数、最小请求间隔、道具与来源方式 | 该行军的加速阶段 |
| 记录 | 时间、操作、请求序号、结果码和计数 | 任务事件 |

出征动作应包含野怪、太阳城和炮台等已实现类型；不要只写“首占”而隐藏真正的动作选择。普通地图的目标输入与活动场景的真实实例身份分开显示。

### 按钮事件

- “立即”：读表单 → TaskSpec → 准备参数 → 后台发送。
- “到点”：读表单 → TaskSpec → 准备参数和截止点 → 后台等待 → 发送。
- “停止”：设置本任务取消标记，阻止后续未发请求，继续接收已发请求结果。
- “连接”：建立 Context 并加载状态，成功后刷新资源与兵阶。
- “断开”：结束该连接的活动任务，显示断开；不能继续把离线计数当真实发送。

网络线程向事件队列写状态，UI 主线程消费事件并更新控件。例如 Python/Tk 可让主线程通过 after 定期消费队列；不要从网络线程直接操作控件，也不要在主线程等待 socket 回包。

### 状态含义

建议显示“待执行、准备中、等待到点、已发送、服务器接受/拒绝、结果未知、已停止”。对于出征，“服务器接受”表示行军创建成功，不代表到达或占领。

离线展示单独标明“演示”，既不连接服务器，也不显示真实使用次数。发送数量只在实际写出后增加，购买响应与加速响应分别归类。

## 三、保存与分发

### 本地文件

普通设置保存选项、次数、间隔与界面状态；凭据独立保存。任务记录可保存目标和返回码，不保存完整登录包、签名或 Token。

重启可以恢复表单值和执行记录，不自动继续未完成的迁城/移民。路径使用程序选定的数据目录，避免固定到某台电脑。

### 一个具体的打包路线

如果采用 Python 桌面方案：

1. 在自己的项目中选定 Python 版本和虚拟环境，明确启动入口，例如 app.py。
2. 按实际代码记录依赖。Tk、加密实现、协议实现分别确认来源；按选定版本准备运行环境。
3. 若选择 PyInstaller，先采用目录分发，按 [官方使用说明](https://pyinstaller.org/en/stable/usage.html) 将入口打包。一个常见命令形态为 python -m PyInstaller --windowed --onedir --name WjdrAssistant app.py。
4. 在打包配置中显式包含程序使用的元数据和自身资源，应用配置按选定路径加载。没有控制台时将可读错误写入程序日志。
5. 交付目录注明入口、支持的客户端版本、配置取得方法、账号导入方式和已知限制。用户在新电脑自行准备会话。
6. 若采用其他技术栈，按相同职责交付运行依赖与资源，不为了模仿目录名称再造一个 runtime。

上述命令只是打包入口示例，不是本 Skill 自带工程的启动命令。用户要求不构建或不测试时不执行这些步骤，交接时写清尚未执行。

## 四、按现象定位问题

| 现象 | 先检查 | 不应直接得出的结论 |
| --- | --- | --- |
| 缺 sdk-app.properties | 读取器路径、字符串来源、文件是否真实生成 | 必须另找现成运行包 |
| 签名失败 | 参数合并顺序、空值、编码、摘要/Base64 顺序、版本渠道 | Token 一定错误 |
| 有 Token 却连不上角色 | 会话有效性、账号/角色 ID、游戏登录字段 | 导入文本就应永久在线 |
| “协议加密变化” | crypt_method、密钥初始化顺序、跨包状态、有效长度 | 服务器必然升级 |
| 界面显示发了但游戏没动作 | 是否演示、是否实际写出、对应业务码、角色与场景 | 发出就代表成功 |
| 有道具却走钻石 | 当前物品 ID、库存是否加载、未知库存策略 | 游戏一定没有道具 |
| 8671 | 实际写入间隔、购买请求是否也计时、返回分类 | 某个固定 ms 保证通过 |
| 高迁结果解析不对 | 当前路径与响应声明，尤其 5633 的 code tag | 所有响应 code 都在 tag 0 |
| 野怪/太阳城出征不对 | 动作 type、monsterid、地图上下文 | 坐标正确就无需附加字段 |
| 时间差一秒或差数小时 | 输入/显示时区、秒取整偏移、调度是否用同一时钟 | 加上毫秒显示就已提高精度 |
| 加速作用到别的队伍 | 是否使用本次出征返回的行军 ID | 队伍槽位就是行军 ID |

## 五、交付说明应该写什么

写清已完成哪些功能、当前客户端证据版本、需要用户提供哪些本地配置、如何启动、哪些运行/测试没有做。真实联网、资源消耗和操作结果只根据实际证据报告。

依据教程完成程序实现，交付与所选技术栈一致的可启动成品和使用说明。
