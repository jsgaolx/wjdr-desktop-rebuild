# 登录、Token 与通信实施教程

按以下流程定位并实现登录与通信。端点、编号和字段是参考，编码前与当前客户端核对。

## 一、先分清身份

| 名称 | 含义 | 用在什么地方 |
| --- | --- | --- |
| game_id / game_key | SDK 应用参数 | 正常 SDK 请求签名 |
| fpid | SDK 账号 ID | 账号会话与 Token 文本 |
| session_key | 可复用的账号会话 | SDK 会话检查、游戏登录 |
| uid | 游戏角色 ID | 选择并登录该角色、所属玩家 |
| 角色 kid | 角色本国 | 角色身份与回本国判断 |
| city_kid | 城市当前王国 | 普通地图上下文与迁城路由 |
| battle instance | 本人进入的活动实例 | 对应战场上下文 |
| march id | 服务器分配的实际行军 ID | 该次行军加速 |

同一账号可能有多个角色。不要用 Token 前半段代替角色 uid，也不要把城市当前王国永远当成角色本国。

## 二、实现正常短信登录

### 2.1 SDK 请求层

从当前 APK 定位应用参数来源、公共请求函数和签名函数。参考 HTTPS 入口：

- 主机：passport-web-gof.campfiregames.cn。
- 客户端入口：/client_api.php?ver=6。
- 会话检查入口：/server_api.php。
- 表单编码：application/x-www-form-urlencoded，UTF-8。
- 参考公共参数包括 game_id、domain、game_version、sdk_version；domain 为 funsdk。

版本、渠道和入口配置从当前客户端取得。

参考签名链路的关键顺序：合并公共参数 → 按参数键排序 → 按 key=value 用 & 连接 → 以应用 game_key 做 HMAC-SHA256 → 将摘要的十六进制文本作 ASCII 字节再 Base64 → 放入 Authorization 的 FP game_id:签名 结构。表单 URL 编码与签名原文的构造分开处理。

特别检查“Base64 原始摘要”还是“Base64 十六进制文本”，以及空值是否参与签名；这类差异会让参数看似正确但全部认证失败。实际实现以 SDK 当前函数为依据，不需要把整个 SDK 搬到桌面程序。

### 2.2 三个步骤及产出

| 步骤 | 参考 method | 关键业务字段 | 得到什么 |
| --- | --- | --- | --- |
| 发短信 | sendCaptcha | mobile、length；fpid/session_key 的空值按客户端构造 | 请求受理或错误 |
| 提交验证码 | loginWithPhoneCode | mobile、code、session_key | fpid、session_key 等 |
| 检查会话 | check_session | session_key、l、service_name | 当前会话所属 fpid 等 |

验证码长度使用当前正常客户端的配置，不自行猜测。短信由用户点击发送，保存的是登录后的会话，不保存验证码。参考 JSON 外层使用 status、data、error；这与游戏业务响应中的 code 不是同一结构。

应用参数获取步骤见 [资料教程](setup.md)。完成本步应能向后续模块提供 AccountSession，而不是让后续代码重新发短信。

## 三、Token 导入、复制与导出

Token 导入导出使用以下格式：

```text
账号fpid----会话session_key
```

分隔符为四个短横线，只在第一次出现处拆分；忽略整段文本首尾空白，不擅自改动会话字符。短示例见 [参考片段](snippets.md)。

界面放“粘贴/导入 Token”“复制 Token”“导出文本”：

1. 导入后创建或更新本地账号记录，状态为“已导入”。
2. 正常 check_session 与角色连接流程仍使用这份会话。导入不等于永久有效，也不等于已经连上角色。
3. 复制/导出是用户主动操作，输出同一种文本格式；会话失效时回到正常登录流程。
4. 本地凭据可用 Windows 当前用户 DPAPI 保存。DPAPI 文件不能当作跨电脑账号包；换电脑使用用户主动导出的会话文本或重新登录。
5. 日志只写状态和错误码，不记录 session_key 或完整 Token。

这只是本地会话复用功能，不包含自动操作模拟器、读取其他人的账号或向外部服务上传 Token。

## 四、从账号到游戏角色连接

参考网关线索为 gofcn-gateway-prod.campfiregames.cn:30101；实际网关、版本、渠道与登录参数从当前客户端取。

连接流程：用账号会话建立游戏登录 → 完成角色加载 → 请求角色列表 3602 → 用户选角色 → 以目标 uid/kid 建立角色连接。登录请求编号为 1，角色加载为 21。角色列表字段包括 uid、kid、name。

游戏登录有独立的字段和签名，不是重复 SDK 的 HTTPS 表单。需要从登录构造函数记录：

- 会话与账号字段。
- 目标角色和王国字段。
- 版本、渠道、设备标识、语言和时间字段。
- 是否创建角色的开关；复用已有账号时使用现有角色路径。
- 签名字段顺序、拼接分隔符、编码和摘要方法。
- 响应的角色身份、连接状态和后续加密材料。

登录响应返回后续 secret，参考字段为 tag 14；使用前核对当前声明。拿到响应即更新解密状态，再处理同一缓冲区里的后续通知。

连接状态至少区分“未连接、连接中、已连接、断开/失败”。只有加载完成才能成为任务使用的 Context。不要因为拿到了账号列表就显示“角色已连接”。

## 五、实现收发层

### 5.1 封包结构

参考 TCP 外层为两字节大端长度，后面是 Sproto packet 的零压缩数据。解压后先解析 header，再处理 body。

| 层 | 参考字段/行为 | 实施要点 |
| --- | --- | --- |
| 外层帧 | 2 字节大端长度 | 保留接收缓冲，逐帧取足；一次 recv 不等于一个包 |
| Sproto header | type/session/userdata 的 tag 为 0/1/2 | 请求编号与请求序号分开 |
| userdata | crypt_method/crypt_length 的 tag 为 0/1 | 决定 body 的解密方式与有效长度 |
| body | 当前请求或响应的 schema | 按字段 tag 与类型编解码，不按 JSON 字符串发送 |

Sproto 的格式和开源参考见 [项目说明](https://github.com/cloudwu/sproto)。它只提供协议编码机制，不提供本游戏的声明、身份或业务操作。

### 5.2 接收与加密状态

接收器需根据包头区分明文/方法 0、方法 1 的 XOR、方法 2 的客户端 RC4 变体。方法 2 的已分析特点为：登录 secret 初始化置换表，置换表状态跨包保存，每包的 i/j 从零开始，按 crypt_length 截断有效内容。

这里应依据客户端函数实现，不能直接换成任意库的“标准 RC4”就假定相同。发送方向与接收方向也要分别核对，不把接收的加密规则盲目套到所有请求。

接收流程：

1. 从缓冲区取得完整长度帧。
2. 零解压，解析 header，定位 body。
3. 根据当前包的 userdata 和连接密钥状态处理 body。
4. 按请求序号找对应响应结构，或按通知类型解码推送。
5. 登录响应立即初始化后续密钥；其他响应投递给等待者/统计器，通知更新状态。
6. 继续处理缓冲区下一帧。

“游戏协议加密格式发生变化”也可能是客户端仅实现 XOR、密钥初始化太晚或状态被重置；先对照具体包头和调用顺序，不先认定服务器已经更新。

### 5.3 序号与并发

最小结构是一条连接、一个读取循环、一个串行写入位置：

- 写入前生成唯一 sequence，并登记它对应的操作与响应结构。
- 记录开始写入时刻，写出完整帧，记录写入完成时刻。
- send 返回 sequence，不必等业务回包。
- call 在 send 之后等待该 sequence 的结果。
- 心跳、角色加载、地图查询与加速各自关联序号，不能把“下一条收到的包”当作当前请求响应。
- 断开后结束当前任务并清理连接状态；不要自动重放之前的迁城或移民操作。

加速“无需等待返回”的意思是发送循环不被单条业务响应阻塞。接收循环仍然工作，以便显示拒绝、资源变化和实际行军变化。
